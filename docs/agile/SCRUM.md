## スプリントと3回ごとのリリース

スプリントは「目標 → 実装/調査 → 検証 → PMレビュー → ふりかえり」の短い作業単位とする。S01はユーザーがGitHub Issues #2/#3/#4と、その後#10/#11の追加開始を承認しActive。開始日2026-10-07、暫定1週間の終了予定は10月13日。S02/S03の対象・日程はそれぞれユーザー開始確認に合わせて更新する。#10のローカル候補と#11のCI/CD構築は承認済み。実公開/CD有効化/Secrets登録は現作業の範囲外。今後の追加PBIは別途確認する。実績から次の容量を見直す。実装が残る状態を、回数合わせで完了扱いしない。

1. PMがスプリントID、目標、対象Issue、受入条件、対象外、担当と依存を提案し、ユーザー確認を記録してから開始する。
2. 各役割は同じ要件IDを使い、担当範囲を宣言して作業する。共有ディレクトリへの競合編集はスクラムマスターが避ける。
3. 成果はPMへ提出し、受入条件ごとに証拠を照合する。採用・要修正・保留を記録する。
4. 終了時に未完了を戻し、次のReady候補と担当案を準備してスプリントを閉じる。次スプリントはユーザー確認後に開始する。見積もり・待ち・不具合から改善を1件選ぶ。
5. 最新運用は各Sprintの `sprint/<id>` → `release/<version>` 集約PRを1本ずつ（3Sprintで3本）、3回受入後にrelease集約 → mainのリリースPRを1本作る。例：S01〜S03がR01、S04〜S06がR02。実リリース周期は3Sprint。欠陥・ブロックを残したスプリントは未完了として扱い、未受入項目をmanifestへ混ぜない。

スプリント内の全PBIが早く受入済みになっても、3スプリントを即完了したことにはしない。S01の承認済み全PBI受入後はReview/振り返り準備へ移り、次の未承認実装は止め、次スプリント候補の要求整理・Issue整理・証拠まとめを行う。

## Readyの定義（DoR）

以下を満たすタスクだけをReady候補へ置く。Readyは要件の準備状態で、ユーザーのスプリント開始確認を代替しない。調査タスクは、変更案を採用する条件と調査の出口を指定すればReadyにできる。

- 要求の根拠と最新仕様へのリンク、問題と対象ユーザー/状態がある。
- 一つのスプリント内でレビュー可能な範囲で、受入条件が観測・試験できる。
- 変更してよいファイル/責務、維持する仕様、対象外がある。
- 担当、依存、必要な環境/資産、検証方法、提出先が決まっている。
- 外部送信・実機・音の聴取など、手元で満たせない条件を識別している。

仕様未決の実装をReadyと呼ばない。まず切り分け・比較・要件確定のタスクへ分割する。

## 完了の定義（DoD）

- 要件IDに対応する変更/成果と、PMが各受入条件を判断できる証拠がある。
- 今回の対象コード・日時・環境・コマンド・結果を記録する。過去の成功・画像を今回の成功へ置き換えない。
- 変更に必要な単体/統合/ブラウザ試験とビルドを実施し、不合格は解消またはPMの条件付き受入として明記する。
- 見た目は現在のコードの画面と連続動作を確認し、停止/復帰・軽減設定など変更に関係する状態を確認する。音は実聴取していなければ未検証、スマホ幅のChromeはスマホ実機とは区別する。
- 確定当落、FIFO、会計、物理、演出尺など維持条件に反していない。仕様変更はPM判断を先に記録する。
- 文書・バックログ・再現方法・未確認事項を更新し、既存変更と今回の成果を区別する。
- PMの受入判定が記録され、次のタスク/引き継ぎが用意されている。

文書だけのタスクはコード試験を要求せず、内容・根拠・リンク・整合性を検査する。一般的な「テスト通過」だけでデザインや体験品質を合格にしない。

## Optional入力と依存の留保

任意の初回版/命名/好み質問の未回答は、承認済み範囲の差分整理・CI準備・要件/証拠照合を止めない。合理的な暫定値と変更可能であることを記録して進める。必須Secrets、明示許可、確定が必要な対象などは、それに依存する操作だけを留保する。留保中も担当へ非依存の次Readyを割り当て、全体停止としない。次Sprintの実装は引き続きユーザー開始確認後。

## ボード・WIP・作業が途切れない運用

状態は `Backlog → Ready → In Progress → Review → Accepted`。スプリントは `Proposed → ユーザー確認 → Active → Review → Closed`。In Progressへの移動は確認済みスプリントの対象内だけ。修正依頼は対象が承認済みの場合に限ってIn Progressへ戻し、未承認なら確認待ちとする。`Blocked` には元の状態、障害、解消担当、次の確認条件を残す。破棄する案は理由を添えて `Dropped` とする。

- 各役割の進行中は原則1件、レビュー待ちは役割ごと1件まで。役割横断の1要件を並行して進める場合も編集所有を分ける。
- 各役割に「次のReady」と「依存しない予備」を最低1件ずつ確保する。キューが1件になった時点で補充を始める。
- 完了提出と同時に、スクラムマスターは確認済みスプリント対象内の次のReadyを具体的に担当へ割り当て、引継ぎ先を記録する。担当の提出で会話を閉じて次割当なしにしない。対象が尽きた場合は未承認PBIへ進まず、Issue整理・提案・証拠まとめへ移る。
- ブロック発見時は、再現・影響・必要な判断を報告し、承認済みの予備だけを開始する。未承認なら事前準備に限定する。解消が必要な本タスクを忘れずボードに残す。
- 全員の依存が同じ障害へ集中したら、承認範囲内の調査/レビュー/ローカル検証へ分割する。新しい対象の追加は提案としてIssueに記録し、ユーザー確認を待つ。

予備キューの型：リードは既存挙動の切り分け/必要な回帰確認、デザイナーは現在の状態別UX比較/受入証拠、スクラムマスターは要件の分割/履歴との整合/検証記録の整備。既存の古いバックログは現行本編で再確認してから選ぶ。

## 引き継ぎとPM受入記録

提出は「要件ID / 変更対象 / 受入条件別の結果 / 今回の証拠 / 未確認・リスク / 次の担当」で統一する。PMは実装量や担当の自己申告でなく、要件と証拠で判定する。

| 記録欄 | 内容 |
|---|---|
| 要件・スプリント | ID、目標、根拠 |
| 提出 | 担当、変更ファイル、対象コード/日時 |
| 受入条件 | 条件ごとの合格/不合格/未検証、証拠リンク |
| PM判定 | Accepted / Rework / Hold、理由、制約、次の担当 |
| 続行 | 次のReady、予備、ブロッカー解消条件 |

通常の継続は、この記録と次のReadyを読んで、前回の未完了を確認してから進める。PMは平日10:00 Asia/Tokyoのheartbeat（automationId `pm`）を作成済み。このスレッドで確認済みスプリントの対象内だけローカル開発・検証・役割への委任・受入を再開する。スプリント未承認の場合はIssue整理・提案・証拠まとめのみを行う。常駐・無限実行は約束しない。スケジュールはクラウド公開を含まず、実行ごとに同じボードと未完了を確認する。

## 現行方針：固定期間を設けない（2026-10-07）

ユーザー「1週間じゃなくていいです。終わったら終わりで」。固定日数・終了予定日は設けず、合意対象のAC・検証・PM受入・集約PRマージが完了した時点で終了する。未完了/未検証/確認待ちは日付や回数合わせで完了にしない。対象変更や持越しはユーザーと合意する。開始前の対象確認、各SprintからreleaseへPR、3Sprint集約後main向けリリースPRを維持する。旧暫定1週間の記述より本方針を優先する。
