# Issue本文・コメントの書き方

2026-10-13のユーザー指示に基づき、本文とコメントを同じ見出し・言葉遣いで書きます。経緯を知らない人にも、目的、確認内容、現状、次の対応が伝わることを優先します。

## 共通の順序

1. やりたいこと：誰がどんな場面で困り、どうなると助かるかを書きます。
2. 確認内容：本文では完了を判断する条件、コメントでは実際に確認した結果を書きます。必要な条件や数値は残します。
3. 今の状況：完了、作業中、確認待ちを区別します。未検証の点や失敗も具体的に書きます。
4. 次に進めること：次の作業と、ユーザーに判断してほしい点を書きます。
5. 参考：必要なPR、確認結果、詳しい資料だけを説明付きでリンクします。

不要な見出しは省けます。同じことを各節で繰り返さず、短いコメントは状況と次の対応だけでも構いません。

## 言葉の選び方

- 固有名詞や内部の管理番号は、読者が対象を特定するために必要な場合だけ使います。タイトルも目的が分かる短い文にします。
- 「AC」「ゲート」「正本」「候補SHA」などを前提にせず、「完了の条件」「開始の確認」「管理する場所」「確認した版」のように具体的に書きます。
- 長い識別子、ファイル一覧、実行ログ、制作経緯は詳しい資料に置きます。本文では結果とその意味を説明します。
- 専門用語を残す場合は、初めて読む人にも意味が分かる説明を添えます。必須の設定名や操作名は、誤操作を防ぐためそのまま残します。
- 敬体で書き、定型の挨拶や大げさな評価は加えません。並列の条件や結果は箇条書きにします。

## 事実と承認の扱い

提案、承認済み、実施済み、未検証を混ぜません。文章の整理を理由に、未承認の作業を開始したり、未実施の確認を合格にしたりしません。過去のコメントは当時の日時と判断を残します。過去の失敗を現在の成功で上書きしません。

既存の本文・コメントを書き直すときは編集前の記録を保存し、重要な条件、数値、制約、関連リンクを確認します。他の人の発言の意味や投稿者は変えません。

## 本文のひな形

```markdown
## やりたいこと

困っていることと、改善したいことを書きます。

## 確認内容

- 完了を判断する条件を書きます。

## 今の状況

作業の状況と、まだ確認できていないことを書きます。

## 次に進めること

次の作業や、判断してほしいことを書きます。
```

## コメントのひな形

```markdown
## 確認内容

- 今回確認した結果を書きます。

## 今の状況

完了したことと、残っていることを書きます。

## 次に進めること

次の作業や、判断してほしいことを書きます。
```

過去のコメントを編集する場合は、先頭に「YYYY-MM-DD時点の記録です。」を付けます。新しい報告には、その報告の確認日時が必要な場合にだけ記載します。
