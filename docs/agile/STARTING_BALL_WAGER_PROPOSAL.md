## 枚数選択と開始玉の分布案（最新）

同日の追加指示：賭ける枚数をプレイヤーが選ぶ。1枚では400玉が約50%、500玉が25%、600玉が10%を基準とし、800玉・1,000玉も設ける。枚数を増やすと400玉の確率が減り、増玉の確率が上がる。上限は最後の発言に合わせ50枚を案とする。

これにより、先の「1枚で400玉／600玉を半々」という提案を置き換える。その後、ユーザーは枚数選択と配分の方向に同意し、1枚時の600玉と800玉が同率になる点の修正を委任した。増玉は大きいほど出にくくする。1枚時を600玉15%・800玉7%・1,000玉3%へ調整し、400玉50%・500玉25%と50枚側の配分を維持する。ユーザー確認後、下記をローカル実装した。長期の遊技・経済バランスの受入は未実施。

| 開始玉 | 1枚 | 50枚 |
|---|---:|---:|
| 400玉 | 50% | 10% |
| 500玉 | 25% | 30% |
| 600玉 | 15% | 25% |
| 800玉 | 7% | 20% |
| 1,000玉 | 3% | 15% |
| 合計 | 100% | 100% |

2〜49枚は、`t = (枚数 − 1) / 49`、各確率を `1枚時 + (50枚時 − 1枚時) × t` とする線形補間案。各枚数で合計100%、枚数を増やすごとに400玉の確率が下がり、それ以外の各結果の確率が上がる。Nodeで全50段階の合計100%と、増玉確率の順序 `500玉 > 600玉 > 800玉 > 1,000玉` を確認済み。表示の丸め値を抽選に使わない。

| 賭け枚数 | 400玉になる確率（表示丸め） | 期待開始玉（表示丸め） |
|---|---:|---:|
| 1枚 | 50% | 501玉 |
| 2枚 | 49.18% | 504.04玉 |
| 10枚 | 42.65% | 528.37玉 |
| 50枚 | 10% | 650玉 |

賭けは1プレイにつき最大1回とする提案。選んだ全枚数は当落を問わず消費し、当選時にチケットを返す案ではない。0枚は抽選せず400玉で開始、選べる有料枚数は1〜`min(50, 所持枚数)`。チケット0枚でも通常開始できる。結果は発射開始前に決めて伝える。

理由：少額でも上乗せの可能性を持ち、多く賭けるほど上乗せに近づくが、50枚でも400玉の可能性を残す。期待開始玉は1枚501玉、50枚650玉で、追加1枚あたりの期待上乗せは約3.04玉。少額の効率が高く、大きく賭けると効率より増玉の確実さと上位結果の確率を買う形になる。この関係が50枚を使う動機になるかは未検証で、50枚を適正価格と断定しない。算術は平均払い出し・勝率・遊技時間やチケット収支の測定結果ではない。

## 換算の現状と検証の限度

既存の `ticketBreakdown(total, 0)` をNodeで呼び、次を確認した。ステージ突破・強化を含めない旧コードの参考値で、本編の獲得実績ではない。

| 累計払い出し | 既存コードの換算 |
|---|---:|
| 0玉 | 0枚 |
| 1玉 | 1枚 |
| 100玉 | 1枚 |
| 399玉 | 1枚 |
| 400玉 | 2枚 |
| 900玉 | 3枚 |
| 1,000玉 | 3枚 |
| 1,500玉 | 3枚 |

今回の会話でこの換算と獲得枚数に上限を設けないことをユーザーが確認。払い出し0玉なら0枚、それ以外は `max(1, floor(sqrt(累計払い出し / 100)))`。発射消費・開始玉・上乗せ玉を含めず、旧ステージ報酬・強化も適用しない。終了時は実際の累計払い出しを精算する。旧仕様のリタイア0枚という記述を本件に自動流用せず、現行の途中終了でも同じ換算を使う。

初回の標準的な払い出し量と長期収支は未測定なので、初回後に必ず賭けられるとは保証しない。チケットの他の用途が機能しない状態では、使わずに残す価値が乏しく、賭けることが常に有利になりうる。既存仕様の有料フロア等との費用比較を伴わず、本案をバランス受入済みにしない。

初回終了時には、獲得枚数・残高・次回に使える用途を示す方針。失敗者には再挑戦、クリア者には同じ台の再遊技という目的の違いを想定するが、再訪率向上は未検証。

## 構造と画面の流れ

対象は遊技外UI。台詳細のスペックの後に、所持枚数、賭け枚数、各開始玉の確率、消費して抽選するボタンを置く。通常の400玉開始ボタンを別に残す。主役は自分が使う枚数と得られる開始玉で、遊技中の未告知当落は参照しない。

枚数選択中は確率を更新し、抽選操作の保存完了後に結果を表示する。保存された結果からプレイ開始するまで任意に確認でき、ロード中の台詳細への復帰や再読込でも同じ結果を使う。演出時間を強制せず、新しい音・光・役物は追加しない。

- [`starting-ball-wager.js`](../../prototype/src/domain/starting-ball-wager.js)：分布を整数重み4900で表現し、表示の丸めを抽選に使わない。賭けなしは乱数を消費しない。
- [`session-ticket-wallet.js`](../../prototype/src/domain/session-ticket-wallet.js)：残高・連番・準備済み結果・遊技中の払い出し・最後の精算を一つの保存レコードで扱う。保存成功後だけ次へ進む。二重操作・再精算は再徴収・再付与をしない。
- [`session-ticket-store.js`](../../prototype/src/app/session-ticket-store.js)：既存依存のCapacitor Preferencesを使用。Webでは同一originのlocalStorage、ネイティブではPreferences。Web Locksがある環境では同じ財布の複数タブ同時遊技も止める。
- [`session-game.js`](../../prototype/src/domain/session-game.js)：開始玉を会計の初期値へ設定し、実払い出しだけでチケットを見積もる。体験・確認用遊技は進行対象外。
- [`starting-wager.js`](../../prototype/src/ui/starting-wager.js) と [`main.js`](../../prototype/src/app/main.js)：任意の賭け、確率・残高・結果表示、保存中の操作抑止、開始と結果の精算を接続。

## 保存・運用

保存キーは `tsukikage-session-tickets-v1`。旧 `tsukikage-profile-v1` を変更・削除せず、旧強化や突破ボーナスを新しい財布へ混ぜない。旧プロフィール残高の移行は今回実装していない。新しい本編の残高は0枚から始まる。

状態は `ready`（徴収・抽選結果を保存済み）→`playing`（盤面ロード完了時に開始記録）→終了精算。ロード失敗や開始前の離脱では `ready` を保持する。実遊技中は獲得枚数の増加時に累計払い出しを保存し、再読込後はその記録分を一度だけ精算する。盤面・持ち玉・保留・遊技の途中状態全体は復元しない。準備済みの増玉を遊技開始後に繰り返し使うこともできない。

保存失敗時は結果を捏造せず、開始を止めるか、結果画面で保存を再試行する。壊れた保存を無言で0枚へ上書きしない。Web Locks非対応環境での複数タブ利用、ネイティブ実機の保存、ページ終了直前の保存失敗時の完全な回収は未検証。

起動は `cd prototype` → `npm run dev -- --host 127.0.0.1 --port 5458`。台を選ぶと残高と開始前チャレンジを確認できる。保存の問題は端末内Preferences/Web Storageの当該キーと画面の保存エラーを確認する。復旧前に当該データを退避し、初期化を通常の対処にしない。

戻す場合は本件のsource差分だけを除外する。新しい保存キーは残し、旧コードでは読み書きしない。公開や既存保存の削除・変換をロールバックに混ぜない。公開・マージは未実施で、今後の具体的な許可を要する。
