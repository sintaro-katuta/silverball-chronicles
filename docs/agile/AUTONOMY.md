# 自律開発と承認の境界

2026-10-20。ユーザーは「開発は自律化し、公開・mainマージ・クラウド更新の承認は残す」を選択した。本書とルートの [AGENTS.md](../../AGENTS.md) を、過去のスプリント開始・対象追加・音声台本の承認待ちより優先する。過去の記録は当時の事実として保持し、新しい開発の停止条件へ転用しない。

## 開発は依頼から検証まで続ける

開発依頼を受けたら、目的、対象、維持する仕様、受入条件を短く記録して着手する。計画を提示しただけで返答を待たず、調査、設計、代表試作、実装、関連する不具合修正、必要な検証、文書化、レビュー可能な差分の準備まで進める。[制作フロー](PRODUCTION_FLOW.md)の工程と[スクラム運用](SCRUM.md)の品質条件は維持する。

| 判断・作業 | 運用 |
|---|---|
| スプリント開始・分割・同じ目的の次スプリント | 対象と受入条件を記録して開始。個別承認を待たない |
| 依頼達成に必要な関連修正・対象追加 | 理由と影響を記録して進める。Issueや計画も必要に応じて更新する |
| 名前、内部構造、ライブラリ選択、比較案 | 既存方針と合理的な仮定で決め、検証結果に応じて修正する |
| 代表試作の展開・ローカル本編への接続 | 依頼範囲に含まれる場合、比較と回帰確認を伴って進める。単体制作だけの依頼を本編差し替えへ広げない |
| PR説明動画の台本・ローカル音声合成・render | 内容を検証結果と照合して制作。台本の個別承認は不要。合成した台本と音声の対応を残す |
| 開発用ブランチ・目的別のローカルコミット | 既存変更を保全し、今回の対象ファイル・差分だけを含めて準備する |
| PR・Issueの外部更新 | 既存または当該依頼の送信許可がある範囲で行う。今回の設定変更を実際の送信依頼とは扱わない |

調査だけ・提案だけ・触らない対象・一時停止などの明示指示は引き続き守る。無関係な新機能やバックログ全件を自動で開始する方針ではない。確定ゲームルールの変更、既存データの破棄、別サービスの契約・有料購入などは自律開発の範囲へ含めない。判断が必要なら具体的な案と影響を示し、それに依存しない作業は続ける。

今回の依頼は運用設定の変更であり、S10や個別の未着手Issueの実装を同時に開始するものではない。以後の開発依頼・継続指示では、スプリント開始のためだけの確認を求めない。

## 公開の承認は残す

次は具体的な対象を示したユーザー承認後に行う。

- mainへのマージ、mainへの直接push、自動マージの予約など、公開を起こすGit操作。
- Cloudflare等へのデプロイ、サイトやPlayCanvas Editorへのアップロード・更新。
- 本番のSecrets・権限・CD設定の変更、公開workflowの手動実行、Releaseの公開。

承認を求める前に、対象差分、検証、未確認事項、公開対象、必要な戻し方をレビュー可能な状態へそろえる。公開候補が決まる前に包括的な許可を求めない。公開待ちを、独立した開発・検証・準備の停止理由にしない。

既存のmainマージ起点CDは維持する。ユーザーが具体的な候補を承認してmainへマージした場合、同じ候補の自動公開にチャットの再承認を要求しない。別候補の再公開・手動実行へ許可を流用しない。開発ブランチへのpushでも公開workflowが起動する場合は公開操作として扱う。

## 検証と報告は省略しない

工程の出口と代表一本の確認は担当者が証拠を見て判断する。現在の版で必要なテスト・ビルド・画面や動作の確認を行う。人による試聴・試遊やスマホ実機を確認できなければ未検証と記録し、機械検査の成功を人間の受入へ読み替えない。未検証の項目があっても、非依存の実装・検証・提出準備は続ける。

釘・球の比較では、固定条件、候補の上限、変更前の説明、試射ごとの結果報告を維持する。報告は承認待ちを意味しない。依頼目的と比較範囲内なら報告後に次の設定へ進む。共有ソースの保全や測定中の変更禁止も維持する。

## Codexのコマンド承認

このリポジトリの `.codex/config.toml` には次の設定を用いる。個人の `~/.codex/config.toml` や他リポジトリの設定は変更しない。

```toml
approval_policy = "on-request"
approvals_reviewer = "auto_review"
sandbox_mode = "workspace-write"
```

通常のローカル作業はworkspace内で実行し、対象となる権限拡張要求は自動レビューへ回す。この設定は公開許可を付与せず、自動レビューの拒否を迂回するものでもない。`never` にして必要な権限拡張まで拒否される状態や、PC全体への無制限アクセスを既定にする方式は採用しない。

プロジェクト設定は信頼済みプロジェクトで読み込まれる。起動時の指定・アプリの権限選択・管理ポリシーが優先する場合があるため、設定ファイルの保存だけで実行中セッションの権限が変わったとは扱わない。再開・新規セッションで有効な設定を確認する。

公式資料：[設定の場所と優先順位](https://learn.chatgpt.com/docs/config-file/config-basic)、[サンドボックスと自動レビュー](https://learn.chatgpt.com/docs/sandboxing)。
