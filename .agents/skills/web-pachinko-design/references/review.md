# 実装後の批評と確認

## 変更に応じて確認範囲を選ぶ

| 変更 | 最低限確認する場面 |
|---|---|
| 図柄・保留・文字 | 通常、変動、停止、小図柄、保留追加・消費、欠字 |
| 戦闘・当落 | 通常→入口→攻防→勝利／ハズレ→復帰。変更した復活分岐 |
| RUSH・BONUS | 突入、残数、当り、ラウンド進行、終了、未告知結果の非表示 |
| 音・時間 | 実再生、ミュート、ポーズ、復帰、連続発火、音の切断 |
| 枠・画面サイズ | 縦画面、台拡大／全体、操作部展開、盤面・出口の欠け |

保存済み画像は比較資料。最新のコードを動かした証拠ではない。試遊サポートで対象シーンを再生し、対象端末サイズと状態を記録する。

## 二段階で見る

**静止画**：最初に見えるものは何か。数字が読めるか。予告の色を識別できるか。人物・文字・光が競合していないか。役物や玉で重要な情報が隠れないか。

**連続再生**：各カットで何が変わったか。攻撃と反応の関係が分かるか。当落前の間に意味があるか。決着時の音・光・図柄が揃うか。外れから通常へ自然に戻るか。繰り返しでも同じ最大演出に疲れないか。

時刻を固定したスクリーンショットだけでテンポを評価しない。音の履歴ログだけで気持ちよさを評価しない。実聴取できない場合は「イベント発火確認のみ、聴感未検証」と残す。

## 機能を壊していないか

演出の途中で一時停止し、表示・音・物理が意図どおり停止するか。非表示から復帰して音が重複しないか。既存の確定結果・払い出し・ラウンド数が変わらないか。試遊の強制再生を通常の確率検証に使わない。

コード変更では対象に合う既存テストを実行する。共通時計や終了処理ならゲーム・演出テスト、見た目ならブラウザ再生・撮影、素材なら欠落・読み込みを確認する。スキル文書だけの変更でゲーム全テストを機械的に実行しない。

## 批評の書式

```text
対象：シーン・展開・端末サイズ・時刻
観察：画像または再生で確認できた具体的事実
影響：何が読み取りにくい／待ちにくいのか
根拠：資料IDと本作の意図。好みの推測なら明示
修正：最も効く少数の変更
再確認：同条件で何が変わったか
未確認：音、実機、端末負荷等
```

例：「迫力不足」だけでは不十分。「技名が顔を覆ったまま保持され、表情と結果の両方が読めない。文字の登場は維持し、保持位置と時間を変える」のように書く。

重大な読み違い・結果不整合を先に直し、次に主役とテンポ、最後に細かな光沢を調整する。同じ画面に装飾を追加し続けない。確認した問題が解消し、関連動作が通れば区切る。実機級の完成や市場での支持を試作だけで宣言しない。
