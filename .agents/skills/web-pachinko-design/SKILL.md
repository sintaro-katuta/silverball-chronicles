# Webパチンコ・デザイン — silverball-chronicles

目的は、架空アニメ「月影機関」のパチンコを、液晶・図柄・文字・音・盤面が連動する体験にすること。対象はスマートフォン縦画面、Web技術で実装しCapacitorに組み込むオフライン作品。ゲームエンジンへの移植を前提にしない。

## 最初に読むもの

プロジェクトルートから `pachinko.md` の冒頭と対象箇所の最新追記、`prototype/DESIGN.md`、変更対象コードを確認する。[プロジェクト対応表](references/project.md)は入口であり、現在の仕様より優先しない。

必要な資料だけ読む：
- 図柄、配色、文字、画面構図、素材 → [visual-patterns.md](references/visual-patterns.md)
- 戦闘、カットイン、予告、役物、RUSH、音 → [motion-and-sound.md](references/motion-and-sound.md)
- 好み、カスタム、煽りの量 → [player-preferences.md](references/player-preferences.md)
- 実装、同期、端末負荷 → [web-implementation.md](references/web-implementation.md)
- 参考動画を比較 → [video-observations.md](references/video-observations.md)
- 検証・批評 → [review.md](references/review.md)
- 根拠の確認・追加調査 → [sources.md](references/sources.md)

## 設計の進め方

1. 対象を通常変動／予告／リーチ／当落／BONUS／RUSH／遊技外UIから特定する。主役、プレイヤーが今知る情報、まだ見せない情報を一文ずつ書く。
2. 既存表現との差を、観察した資料IDとともに記録する。「実機に存在」「支持の根拠あり」「この作品への提案」を混同しない。記事の転載数や再生数だけで好みを断定しない。
3. 新しい演出では、粗い絵コンテとタイムラインを先に決める。各区間に主役、構図、文字、音、光、入り方・保持・抜け方、終了後の状態を記す。色違いだけでなく視線や場面展開の異なる案を必要に応じて比較する。小修正には大きな企画書を作らない。
4. 既存素材・描画層を再利用する。必要な絵がない場合は、必要な構図・切り抜き・差分を具体化する。高品質な絵から簡素な代替キャラクターへ途中で切り替えない。
5. 代表的な一本を実装・再生し、静止画と時間変化の両方で批評する。見た目の完成度を確認してから別シーンへ展開する。変更のためのユーザー確認を工程ごとに要求しない。

## この作品で守る判断

- パチンコの主役は盤面と液晶。LPのヒーロー、説明カード、章番号、見出しの大きさで迫力を代用しない。設定や強化画面には通常の操作UIを使える。
- 厚みのある図柄、金属表現、発光、グラデーション、強い文字は用途に応じて使う。一般Webデザインの装飾禁止を持ち込まない。一方、背景・顔・図柄・文字・枠を常に同じ強さにしない。
- ブランド色／世界観の色と、期待を知らせる色を区別する。色の意味や確定表現を、場面ごとに勝手に変えない。業界共通の厳密な色順位・信頼度を捏造しない。
- 通常時は図柄と保留、発展時は物語、決着時は結果を主役にする。単に画像を拡大・振動させ続けても攻防にはならない。
- 期待感の演出は既存の確定した抽選結果を提示する。演出の強弱、PUSH、素材ロード、フレーム落ちで再抽選しない。出玉・保留・停止順・物理仕様を美術改修に紛れて変更しない。
- 既存のコース別テンポ、ポーズ、試遊サポートを利用する。参考機種の秒数・確率・役物による抽選をそのまま導入しない。
- 参考の絵・キャラクター・音声を製品素材へ流用しない。構図や情報伝達の原理をオリジナル素材へ翻案する。

## 完了条件

該当する通常／期待／当落／復帰を実際に再生し、[レビュー手順](references/review.md)で確認する。ソースコードや音イベントのログだけで「見た」「聴いた」と報告しない。確認できない環境・音声・連続再生は未検証と明示する。

報告には変更の意図、参照ID、確認した画面・条件、残る問題を短く残す。ユーザーが採用した設計判断は `prototype/DESIGN.md` に適用範囲付きで整理する。AIの仮説や一度の好みを全画面の禁止規則へ昇格させない。
